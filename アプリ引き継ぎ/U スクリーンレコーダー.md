## 2026-07-31 夕方 — **このMacで録画に成功した**（決着）

DSへの委任をやめ、このMacで直接直した。**18:07に `Saved Screen 2026-07-31 18.07.33.mov — 879 frames, 14.4 MB` を確認。映像の再生も本人確認済み。**

### 何が原因だったか（2つ。どちらか片方だけでは直らない）

**① `build.sh` の署名が、バンドルとして成立していなかった**

修正前の `.app` を `codesign -dv` で調べた結果:

```
flags=0x20002(adhoc,linker-signed)   ← build.sh の codesign が効いていない
Identifier=ScreenRecorder            ← Info.plist の com.screenrecorder.app ではない
Info.plist=not bound                 ← 身分証が署名に結びついていない
Sealed Resources=none                ← 中身が封をされていない
→ code has no resources but signature indicates they must be present（検証失敗）
```

macOSは画面収録の許可を**アプリの身分証（bundle identifier）に結びつけて保存**する。それが署名に結びついていないため、**許可を与えても使う瞬間に無効化され、一覧から項目ごと消えていた。** 何度追加しても同じことが起きる。

**② アプリに、許可を要求する機能が無かった**

`main.swift` は `SCShareableContent.current` を呼ぶだけで、拒否されると `-3801` を受けて「Screen recording permission needed」と表示するだけだった。**`CGRequestScreenCaptureAccess()` を呼んでいないので、macOSは許可ダイアログを出さない。** 結果、ユーザーは「＋」で手作業登録するしかなく、その手動登録は①のせいで定着しない ── 完全な袋小路。

### 直した内容（`アプリ本体/screen-recorder/` に反映済み。**ds-appsへの反映は未**）

- `Sources/ScreenRecorder/main.swift`: `import CoreGraphics` を追加。`start()` の冒頭で `CGPreflightScreenCaptureAccess()` → `CGRequestScreenCaptureAccess()` を呼ぶようにした。理由をコメントで残してある。
- `build.sh`: `codesign --force --deep --sign "$CERT"` → **`codesign --force --sign - --identifier com.screenrecorder.app`**。あわせて `codesign --verify --strict` をビルド手順に組み込み、**署名が壊れていればビルドが失敗する**ようにした。出力先を `~/Desktop` → **`/Applications`** に一本化（2つ並存して混乱したため）。

### ★踏んではいけない地雷（今日新しく分かったもの）

- **画面収録の許可ダイアログには「許可」ボタンが無い。** macOSの仕様で、画面収録だけは必ず「システム設定を開く」へ飛ばされる。Claudeは「許可を押してください」と誤案内した。正しくは **［システム設定を開く］→ 一覧の該当アプリをオン → 終了して再度開く**。
- **拒否の記録が残っていると、`CGRequestScreenCaptureAccess()` は何も出さずに false を返す。** 詰まったら `tccutil reset ScreenCapture com.screenrecorder.app` で記録を消してからやり直す。
- **アプリを更新したら、必ず古いプロセスを終了させてから起動し直す。** 起動しっぱなしだと古いバイナリが動き続け、テストが1回無駄になる（実際にやった）。
- **ターミナルからバイナリを直接起動すると、許可の主体がターミナルになる**（ように見える挙動をした）。実機テストは必ず `.app` をダブルクリック（またはopen）で行う。
- **macOS Sequoia以降は、画面収録の許可を定期的に再確認してくる**（「システムプライベートウインドウピッカーをバイパスして…」という窓）。出たら「許可」でよい。壊れたわけではない。
- **`Info.plist` に `CFBundleIconFile` が無いので、アプリのアイコンが白紙になる。** Finderやシステム設定の一覧で見つけにくい。実害は無いが、探すときに困る。直すなら Info.plist に追加。

## 2026-07-31 夜 — 肉声対応の見立て（実装は未着手）

**用途が確定した**: 会議は **Teams が主、Zoom もあり、相手によっては LINE**。3つとも「相手＝システム音声／自分＝マイク」で形は同じ。**対面のみという可能性は消えた＝マイク1本では足りない。**

**macOSは Tahoe（macOS 26）**（本人確認済み）。よって `SCStreamConfiguration.captureMicrophone`（macOS 15+）が使える。

### 検討した選択肢

```
既製解｜探した語: BlackHole, Aggregate Device, LadioCast, ScreenCaptureKit captureMicrophone,
                 QuickTime オーディオ収録, Command+Shift+5 マイク
       OS標準: Command+Shift+5 → マイクかシステムか片方だけ。両方は不可
               Audio MIDI設定のAggregate → **チャンネルを並べるだけで混ぜない**
       既存アプリ: LadioCast（無料ミキサー）で4ch→2chに合成可
       手持ち: BlackHole導入済み、機器セット2つ作成済み
　→ 今回アプリに足す理由: Tahoeなら数十行で済み、毎回のルーティング設定が不要になるため
```

| 案 | 判定 |
|---|---|
| ㋐ アプリに `captureMicrophone` を足す | **本命**（macOS 26で可） |
| ㋑ LadioCastで合流 | 次点。アプリ無改造だが会議のたびにルーティング確認が要り、ミスると無音に気づかない |
| ㋒ 音声だけボイスメモ等で別録り | 壊れにくい。議事録目的なら映像が要らない可能性もある |
| ㋓ マイクのみ | **却下**（オンライン会議では相手の声が入らない） |

### ★重要な発見（作成済み機器セットの落とし穴）

**Audio MIDI設定の Aggregate Device は、チャンネルを「並べる」だけで「混ぜない」。** 作成済みの「会議録音入力」（MacBook Proマイク＋BlackHole 2ch）は合計4chになり、画面収録が先頭2chしか録らなければ **BlackHole側（相手の声）が丸ごと落ちる**。㋑を採るならミキサー（LadioCast等）が別途要る。

**Multi-Output Device（「会議用音声出力」）を使うと、キーボードの音量キーが効かなくなる**（macOSの仕様）。会議中の音量調整はアプリ側で行うことになる。

### ㋐を実装する場合の中身

1. `Info.plist` に `NSMicrophoneUsageDescription`（**無いと権限要求の瞬間にクラッシュする**）
2. `SCStreamConfiguration.captureMicrophone = true`
3. `SCStream` に `.microphone` 出力を追加
4. `AVAssetWriter` に2本目の音声入力

## 2026-07-31 夜 — App Store 公開の構想（本人発案。**判断は保留**）

本人から「ここまで頑張ったのでApp Storeに出してみようか」という発案。**本人の方針は「まずはこのMacで安定稼働させることが先」で、これは順序として妥当。** 以下は判断材料であって、着手を決めたわけではない。
