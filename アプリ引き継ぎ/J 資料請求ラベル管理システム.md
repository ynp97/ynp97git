### J-3. 機械を移すときのデータ移行（2026-08-16 実データで実施・成功）

> [!important] ★このアプリのデータは Chrome の localStorage にある。**ファイルコピーでは運べない。**
> `scripts/migrate_app_data.sh` の対象は Application Support / `.app` / Desktop で、**Chrome は入っていない。** そのため 2026-08-15 の M5→15インチAir 移行では、**アプリだけ入って中身が空**になった。同じ穴は localStorage を使う他のHTMLアプリ（三本立てTODO 等）にも空いている。

**正しい手順**（2026-08-16 に実データで通した）

1. **旧機**（M5）でDockのオレンジ「ラ」から **1枚だけ**開く。既に開いている画面があれば先に全部閉じる（多重ウインドウの既知症状。J:32/33）。
2. 「**履歴・バックアップ**」タブ → 一番下の「**バックアップ（全データ）**」カード → 「**全データをJSON書き出し**」。
3. できた `label_backup_YYYY-MM-DD-hh-mm.json` を新機へ運ぶ。**個人情報なのでメール・クラウドに乗せない**（BENJAMIN等の物理経由）。
4. **新機**でDockの「ラ」から開く → 同じカードの「**JSONから復元**」でそのファイルを選ぶ。
5. 「復元しました。」が出たら**件数を照合**する。

> [!warning] ★押すボタンを間違えない
> 同じタブに「**送付済みをJSON書き出し（学校台帳用）**」があるが、**これは復元用ではない。** 送付済み一覧だけで、取り込み済み記録・辞書・印刷待ちが落ちる。
> **ファイル名で見分ける** ── 復元用＝`label_backup_` ／ 学校台帳用＝`school_ledger_sends_`。

- **確かめ方**＝旧機で控えた件数と一致するか。2026-08-16は **35 と 1210** で一致を確認（本人）。
- **復元は `state` を丸ごと置き換える**（`state=Object.assign(base(),j)`）。**中身のある側では実行しない。**
- `~/Desktop/AI関係/ラベル管理` の `history.sqlite3` は **Streamlit時代の旧データ**で、現行アプリは読まない。2026-08-16に15インチへ復元したが、**空の原因ではなかった**（原因はlocalStorage）。旧データとして置いてあるだけ。
- **★ここが最も慎重を要する理由** ── localStorage には**二重発送防止の送付済み台帳**（`state.sent`）が入っている。空のまま発送作業をすると、**既に送った人へもう一度送る**。学校の紙の発送前に必ず運ぶ。
- **Chromeのプロファイル分岐に注意**（J:32）。ランチャーは `--profile-directory=Default` ＋ `?app=1` に固定してある。**書き出しも復元も、必ずDockのランチャー経由で開いた画面で行う。** 別経路（拡張機能・直接file://を開く等）で復元すると、別の保存先に入って空のままに見えることがある。

### J-4. 起動の重さと「印刷ボタンが効かない」への対応（2026-09-04）

**① 起動時のCDN読み込みを廃止（測定済み）**

- 旧: `<head>` に `<script src="https://cdnjs.cloudflare.com/.../xlsx.full.min.js">` を直書きしていた。**これは描画をブロックする**ので、ネットが遅い日は読み終わるまで画面もボタンも出ない。ヘッドレスChromeでCDNを8秒遅延させて再現したところ、**画面が出るのもボタンが効き始めるのも一律8.1秒後**だった（＝遅延がそのまま起動時間になる）。
- 新: 起動時は読まない。`ensureXLSX()` を作り、**①でExcelファイルを選んだ時だけ**読む。読む順は **同フォルダの `xlsx.full.min.js`（新規に配置・881KB）→ 無ければCDN**。
- 結果: **起動時の外部リクエストはゼロ**（Playwrightで確認）。ローカル版から `XLSX 0.18.5` の読み込み成功も確認。**Excel取り込みがオフラインでも動くようになった**（従来は要ネット）。
- 注意: データ量は起動の重さの原因では**なかった**。送付済み1500件＋取り込み済み6000件＋名簿2000件を積んでも描画は0.7秒（実測）。

**② 印刷ボタン: `alert`／`confirm` をやめ、画面内バナーに変えた**

- 症状: ③の「印刷する」を押しても**何も起きない**（キューには人が並んでいる状態で発生）。
- コード自体は正常だった。ヘッドレスChromeで同じHTMLを動かすと `window.print()` まで到達し、24面1ページ・宛名24件が正しく組まれる。**つまりJSの不具合ではない。**
- 旧コードは「押しても何も起きない」に化ける経路を2つ持っていた。どちらも**ブラウザのダイアログ頼み**である点が原因。
  1. キューが空 → `alert()`。Chromeがダイアログを抑止していると**黙って消える**。
  2. 送付済みが混ざる → `confirm()`。抑止されると **`false` が返り、そのまま `return`** して無反応になる。
- 対策: 両方とも既存の `showFlow()` バナー（画面内・抑止されない）に置き換えた。二重発送の警告は**「やめる／それでも印刷する」の2ボタン**にしたので、安全弁は落ちていない。
- さらに `runPrint()` を新設し、**`window.print()` を呼ぶ直前に「印刷ダイアログを開きます ／ 時刻 ／ 宛名N件を組みました」をバナー表示**する。例外は握らず `catch` して文言を出す。
  - **これで切り分けができる**: 押してバナーが出る→JSは正常で、Chromeの印刷プレビュー側の問題（バナーに書いた通り ⌘P で代替可）。**バナーも出ない→クリック／ハンドラ側の問題。**
- 検証: 空キュー・送付済み混在・上書き印刷の3経路をPlaywrightで実行。**ダイアログは1つも使われず**、バナー文言・ボタン・`window.print()` 到達・ラベル生成数まで確認済み。

**③ ランチャーから `python3` の呼び出しを削除**

- 旧ランチャーは、固定パスをURL化するためだけに毎回 `python3 -c 'urllib.parse.quote(...)'` を起動していた。macOSの `/usr/bin/python3` はCommand Line Toolsのシムで、**起動そのものに時間がかかる**（本人の症状は「白いウインドウが出るまでが長い」＝ページではなくランチャー側）。
- 新: zshの `${HTML// /%20}` で空白だけ置換。**サブプロセスなし。** 日本語はChromeがそのまま扱える。
- あわせて **`?app=1&t=<開始epoch秒>`** を渡すようにし、HTML側でヘッダーに **「／起動 X.X秒」** を表示する。**Dockを押してから画面が出るまでの実測値が毎回見える。**
- 変更したのは `セットアップ_古い削除とDock追加.command` 内の `run` と `ラベル管理_ウインドウで開く.command` の両方。**★Dockの.appに反映するには「セットアップ_古い削除とDock追加.command」の再実行が必要**（J:32と同じ）。

**まだ確定していないこと**
