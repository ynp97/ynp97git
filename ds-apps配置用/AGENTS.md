# AGENTS.md — ds-apps で作業するAIへ

このリポジトリは、15インチMac（DS実装機）と現在のMac（設計・指示・検品）をつなぐ受け渡し経路。
実装はこちらで行い、方針判断と `main` へのマージは現在のMac側が行う。

## 完成条件（これを満たさずに「完了」と書かない）

**`docs/作業票/○○.md` というファイル自体が存在しないpushは禁止。** 「内容が薄い」以前に、ファイルを作らずに済ませることはできない。テンプレートは `docs/作業票テンプレート.md`。

作業票の「ビルド結果」「動作確認」には、**実際に実行したコマンドと、その出力を貼る**。

- 「未ビルド」「未実施」「たぶん動く」のまま push しない。
- 通らなかった場合は、通らなかった事実とエラー全文を貼る。それは正しい報告であって失敗報告ではない。
- 出力を貼れない事情があるなら、その理由を書く。黙って空欄にしない。

## 指示の実行原則

指示された操作は額面通りに実行する。似た効果に見える代替手段に勝手に置き換えない
（例:「リポジトリを非公開(Private)にする」と言われたら Private 化する。
アーカイブ（archive）は読み取り専用になるだけで公開状態は変わらないため、代わりにならない）。
指示の意味に迷ったら、勝手に解釈を広げず作業票の「懸念・相談」に書いて止める。

## A層｜機械チェック（push前に必ず自分で回す）

TypeScript / Node の場合:

```
npm install
npx tsc --noEmit
npm run build
```

Swift / Mac アプリの場合:

```
swift build
```

Xcodeプロジェクトなら `xcodebuild -scheme <スキーム名> build`。
テストがあるものは合わせて実行する。

## B層｜自動チェック（GitHub Actions）

push すると `.github/workflows/check.yml` が走る。Actions タブで結果を確認する。
赤（失敗）のまま「完了」と報告しない。直すか、直せない理由を作業票へ書く。

## C層｜相互チェック（別セッションでのレビュー）

**実装したセッションで自己検品しない。** 新しいセッションを立て、そこへ渡すのは次の2つだけ。

1. 差分（`git diff main...HEAD`）
2. その作業の完成条件

**台帳・Vault・リポジトリ全文は渡さない。** 渡すと固定コストが膨らみ、委任した意味が消える。

レビュー役へ聞くこと:

- 差分は完成条件を満たしているか。満たしていない箇所はどこか
- 仕様にない機能を勝手に足していないか
- 実データ・APIキー・証明書が混入していないか
- エラー処理の抜け、境界値、失敗時の挙動

指摘が出たら直してから push する。レビューで出た要点は作業票の「懸念・相談」へ残す。

## 急ぎのとき

「急ぎ」と指示された場合は **C層（別セッションレビュー）を省略してよい**。
ただし **A層は省略しない**。作業票に「急ぎ指示によりC層省略」と一行明記する。

## 禁止

- `main` への直接 push（作業は `ds/作業名` ブランチを作る）
- 実データ（氏名・住所など）・APIキー・証明書・Vault の混入
- 委任されていないアプリを `apps/` へ追加すること
- 動作を確認していないものを、確認済みとして報告すること
- 作業票ファイルを作らずに push すること
- 指示された操作を、似た代替手段に勝手に置き換えること

## 迷ったとき

仕様が曖昧なまま推測で実装を広げない。作業票の「懸念・相談」へ書いて止める。
判断は現在のMac側（本人）が行う。
