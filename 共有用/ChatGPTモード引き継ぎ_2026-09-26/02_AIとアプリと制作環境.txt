## 6. 検証で分かった限界

### RAGはVaultを丸ごと読む仕組みではない

Vault QAは、質問と意味が近い断片を上位から数個拾う。ノート全体や正本の優先順位を、人間と同じように理解するとは限らない。

### 新旧や重要度を自動では判定できない

過去テストでは、8月の予定を尋ねた際、古い計画から「SNS毎日100件・NPO設立」などを現在方針のように回答した。正しい現在地は、📌事実と前提、🔭検討中プロジェクト、🗒相談ログの最新決定を優先する。

### 小型・ローカルモデルは拾った断片から作文しやすい

流暢さを根拠と考えない。資料にない数字、出典、製品、価格、出来事を補わせない。確認できない場合は停止させる。

再発防止として、`.obsidian/plugins/copilot/data.json`の共通`userSystemPrompt`と`/ynp97`の両方に、①モデル内部の学習記憶は固有対象の検証済み根拠ではない、②実際の参照文脈なしに「公式で確認」と言わない、③根拠を示せなければ前回の断定を撤回して終了、④似た名称・新旧表記を置換しない、を追加した。

### LM StudioアプリのSystem PromptとCopilotは別入口

LM Studioアプリのチャット欄で設定したSystem Promptが、CopilotからAPI経由で呼ぶ回答へ自動適用されるとは限らない。そのため、Copilot側の `/ynp97` にも捏造防止ルールを記載している。

### 10-1. 15インチ側で同期が止まっていた件と復旧（2026-08-20）

> [!important] 症状と真因（次に同じことが起きたら、まずここを見る）
> **症状**: M5で書いたノートが15インチAirに反映されない。8/19のセットアップ直後の1回で同期が止まり、24時間以上、自動コミットもプッシュもプルも一切走っていなかった。
> **真因**: **15インチ側の`master`ブランチに追跡先（upstream）が設定されていなかった。** 8/19のセットアップでは`git push -f origin master`で強制プッシュしただけで`-u`を付けなかったため追跡設定が作られず、Obsidian Gitが「どこへ送り、どこから取るか」を自力で決められない状態だった。10分タイマーはこの問いに答えられないので、**無人のまま静かに失敗し続けていた**（エラーが本人の目に触れなかった）。
> **M5側は正常だった。** GitHubには`vault backup: 2026-08-19 11:34`と`2026-08-20 18:06`が届いており、届いていなかったのは15インチ側だけ。

- **切り分けの第一手（更新）**: 同期が止まったら、まず対象機で `git branch -vv` を実行する。`master`の右に`[origin/master]`が**出ていなければ追跡先が未設定**＝今回と同じ原因。`git push -u origin master` で設定する。設定されたことは、同コマンドの最後に`branch 'master' set up to track 'origin/master'.`と出ることで確認できる（2026-08-20に実際に確認）。
- **復旧の手順（実行して通ったもの）**: ①ディスク上の全内容を`git add -A` → `git commit`で一度登録する（未登録ファイルが大量にあると`untracked working tree files would be overwritten by merge`でpullが止まるため）②`git config pull.rebase false`（merge方式に固定。Obsidian Git側もmerge）③`git pull origin master`④衝突ファイルを統合⑤`git add -A` → `git commit` → `git push -u origin master`。
- **コンフリクトの実地初発生（8/19の「未検証」が解消）**: `AGENTS.md` `CLAUDE.md` `🗒 相談ログ（追記式）.md` の3件で発生。いずれも両機が**同じ箇所へ別の追記をした**ことが原因（Air＝`pop97`追加、M5＝`sos97`追加）。**どちらも捨てず両方残す**方針で統合し、モード番号を`pop97`＝⑬・`sos97`＝⑭に採番し直し、合図表冒頭の「13モード」を「14モード」へ直した。相談ログは日付の新しい順（8/20→8/19）に並べて両方保持。
- **★AI側の反省（次に同じ作業をするAIへ）**: ①**Cowork経由で`git status`等を叩くたびに`.git/index.lock`が残り**、そのたびに本人に`rm`を依頼することになった。**調査もターミナル側に寄せ、Cowork経由でgitコマンドを叩かないこと**（読み取り系でもロックは残る）。②原因を確かめる前に`git pull`を条件だけ変えて繰り返し、手戻りを増やした。**同じ症状が2回出たら実装をやめる**（振る舞いの原則1）を、この件では守れていなかった。最初に`git branch -vv`を見ていれば一手で分かった。

## 9.5 安価APIとの比較検討（2026-07-18・検証は明日）

> [!important] ローカルAIを選んだ動機は「値段」であって機密ではない（本人確認 2026-07-18）

### 9.5.5 検品を4層に分けてトークンを使わない相互チェックにする（2026-07-30）

**問題**: 15インチMac(DS)の成果物をChatGPT/Codexで検品すると、一番高い週間枠を検品に使うことになり、DSへ逃がした意味が消える。

**方針**: 相互チェックをAI↔AIに限定せず、コストで4層に分ける。判断力の要らない部分を無料の機械チェックへ寄せる。

- **A層 機械チェック（トークン0・費用0）**: build・型チェック・テスト。実際は「チェック能力不足」ではなく**完成条件が緩い**のが穴だった（作業票に「未ビルド・未実施」と書いたままpushできていた）。作業票に実コマンド出力を貼らせて塞ぐ。
- **B層 GitHub Actions（実質無料）**: pushごとに自動実行。非公開リポジトリはFreeプランで月2,000分。UbuntuランナーはTS/Nodeなら使い切らない。macOSランナーは倍率が高いので、Swift検査が必要になったら15インチMac自身をセルフホストランナーにする（セルフホストは課金対象外）。
- **C層 DS↔DS相互チェック（1円未満）**: 記憶のない別DeepSeekセッションが差分をレビュー。渡すのは差分と完成条件だけで、台帳全文は渡さない（9.5.1の固定費の教訓）。Codex週間枠に触らない。実装したセッションに自己検品させない。
- **D層 本人・Codex**: マージ判断と、A〜Cが赤を出したときだけ。

**足枷にしない設計**: ブランチ保護（必須ステータスチェック）は意図的に設定しない。赤✗は掲示であって門ではない。`[skip ci]` で検査自体を飛ばせる。「急ぎ」指示でDSはC層を省略してよい（A層は省略しない）。急いで自分で直すときはCodex直行で `アプリ本体/` を触り、ds-appsは経路に入らない。

**残る懸念**: DSがDSを検品すると同系列モデルゆえ盲点が相関する。お金・実データ・教会向け成果物は本人のゲートを残す。またチェックを増やすと読む物が増えるため、縛りはトークンよりレビュー時間になる可能性がある（A/B層の利点は出力が合否1ビットであること）。

**成果物**: `ds-apps配置用/`（Vault内）に `AGENTS.md`／`作業票テンプレート.md`／`check.yml`／`配置手順.md` を作成済み。ds-appsへの配置先は配置手順.mdの表のとおり。置けば15インチ側は `git pull` だけで受け取る。

## 9.6 OpenClaw（DS）を画像対応にする＝Qwen3-VLへセッション内切替（2026-07-21 成立・実画面確認）

OpenClawの既定モデル `deepseek-v4-flash` はテキスト専用で画像を見られない。スクショを見せて相談したいとき（例: FCP操作を教わる）は、**同一セッション内でローカルのQwen3-VLへ切り替える**。DeepSeek（クラウド）は画像時もVRAMを使わないので、テキスト＝DeepSeek／画像＝ローカルVLの二枚看板が両立する。

**前提**: LM Studioに `Qwen3 VL 30B A3B Instruct`（`qwen3_vl_moe`, MLX, 約17GB）がダウンロード済み（確認 2026-07-21）。

**設定（`~/.openclaw/openclaw.json`）**: DeepSeekは触らず、LM Studioプロバイダを追加するだけ。純正バックアップ（`openclaw.json.bak` 等）も自動で残る。
- `models.providers` に `lmstudio` を追加：`baseUrl: http://localhost:1234/v1` ／ `apiKey: "lmstudio"`（ダミー・ローカルは認証なし）／ `api: "openai-completions"` ／ `params.preload: false`（LM StudioのJIT/手動ロードに任せる）／ モデル `id: "qwen3-vl-30b-a3b-instruct-mlx"`、`input: ["text","image"]`、`contextWindow: 32768`。
- `agents.defaults.models` に `"lmstudio/qwen3-vl-30b-a3b-instruct-mlx": { "alias": "Qwen3-VL" }` を追加。`model.primary` はDeepSeekのまま。
- モデルの正確な`id`は `curl http://localhost:1234/api/v1/models` の `"key"` で確認できる（今回は `qwen3-vl-30b-a3b-instruct-mlx`）。書式の正本は [OpenClaw LM Studio doc](https://docs.openclaw.ai/providers/lmstudio)。

**使う手順（毎回）**:
1. LM Studioで `Qwen3 VL 30B A3B Instruct` をLoad。`preload:false`なので**手動ロードが確実**。ロード時の **Context Length は 16384〜32768**（画像1枚は約1〜2千トークン。数枚でも十分）。「Remember settings for …」にチェックしておくと次回自動。
2. **32GBメモリでは最大コンテキスト（262144）は不可**。本体17GB＋巨大KVキャッシュで溢れる。16384（他アプリ併用時）〜32768が安全圏。もっと長くしたいときだけ `KV Cache Quantization` をON。
3. OpenClawで**新しいセッション**を作る（画像は履歴を食うので使い回さない）。左下のモデルを **Qwen3-VL** に切替。**スクショは1枚ずつ**貼って質問。
4. 画像用が済んだらテキストはDeepSeekへ戻す。

**つまずきの正体（2026-07-21）**: 最初に失敗したのは「未ロード」が主因（LM Studioが `Select a model to load` のままだった）。コンテキスト長不足ではなかった。以後は「まずLM Studioで実際にロードされたか（モデル名が表示されるか）」を最初に確認する。

### ㋐ 先に確認しておく3つの制約（設計の前提）

1. **「知識の完全共有」と「コストカット」は原理的に対立する。** 全文を読ませればトークンを食う。だから2026-07-31に索引方式へ移した（95,500字→約4万字）。**目標は「全員が全部を読む」ではなく「全員が同じ入口に着けること」と置き換えたほうが実現できる。** 現に、いま同じ入口を通れていないAIがいる（下記㋑）。
2. **「全自動」の上限は権限。** TCC（画面収録・マイク等）の承認とTouch ID・パスワードは、**どのAIも代行できない**（§1）。全自動に寄せる設計とは、**権限が要る操作を経路から追い出す**設計のこと。
3. **司令塔を置かない代わりに、判断の基準を文書に置くしかない。** 基準がないと、その場にいるAIがその場のノリで環境を選ぶ。**この能力表§2の逆引きが、その基準の第一版。**

## 2. 現在の開発方針

いまは、アプリそのものを増やすより、各アプリを「どこからでも再開できる状態」に整える時期。

共通方針:

1. まずこのノートに現在地を書く。
2. 実体コードの場所を書く。
3. 起動方法を書く。
4. 次の一手を1つに絞る。
5. Vaultにあるものと、Vault外にあるものを混ぜて扱わない。
6. ユーザー方針として、今後のアプリ関係の実体は原則 `~/Desktop/AI関係/` の中に展開する。デスクトップ直下にアプリ用フォルダやリンクを増やさない。

POP関連については、送金前クリティカルを進める時期。

優先順位:

1. 出席簿: 保存と復旧を安定させる
2. POP関連: 送金前ゲートと「俺は世界を変える！」の役割を整理する
3. シランガナ: 薄い文字OCRの失敗原因を見える化する
4. Graveyard: 自分用アーカイブとして取り込みと整理を安定させる
5. 元の作業場所と `アプリ本体/` の役割を整理する

開発では、まず「動くものを増やす」より、「何を実行させたいか」を絞る。

### Cubase 15 オーディオシステム（★重さの原因になりやすい・最初に見る）

場所: `スタジオ → スタジオ設定... → オーディオシステム → 詳細設定`。変更後は必ず「適用」を押す。

- **「マルチプロセッシングを有効化」は必ずオン。** オフにするとCubaseは**CPUコアを1個しか使わない**。M5・32GBの機体でも全体が明確に重くなる。2026-08-20にオフになっているのを発見し、オンへ修正して解消した。
- **「ASIO-Guardを有効化」もオン**、レベルは「標準」。マルチプロセッシングがオフだとASIO-Guardは選択すらできずグレーアウトするので、必ず①マルチプロセッシング→②ASIO-Guardの順で入れる。
- 効いているかの確認: 適用後、上部の「ASIO-Guard レイテンシー」表示が `0.000 ms` から実際の値（例: 170.667 ms）へ変わる。`0.000 ms` のままならASIO-Guardは効いていない。
- プロセッシング精度: 32 bit float。
- 現在のオーディオインターフェースは **MOTU M2**（UR44Cは不調のため使用中止。経緯は [[🎛 音楽制作環境 更新ログ]] 2026-08-19）。
- バッファーサイズは大きめ（入力88.4ms／出力85.9ms＝4096サンプル相当）。ミックス中はこのままでよいが、**鍵盤やギターを弾く・録る日は** `スタジオ設定 → M2 → コントロールパネル` で256〜512へ下げる。下げないと約0.09秒遅れて聞こえる。

#### Cubase → Logic → Cubase の制作フロー

- Cubaseを曲構成・テンポ・コード・最終ミックスの正本とする。LogicはSession Playerによる演奏生成に使う。
- 往路: Cubaseコードパッド → コードトラックへ配置／録音 → コードをMIDIへ変換 → Logicへ渡す → Logicのコードトラックで解析 → Session Playerに演奏させる。
- 復路: LogicのDrummer／Bass／Keyboard等のSession Playerリージョンを通常MIDIへ変換 → Standard MIDI Fileとして書き出す → Cubaseへ読み込み → Cubaseで音源差し替え・編集・ミックス。
- 一つの `Chord Bridge` アプリに「Cubase → Logic」と「Logic → Cubase」の二方向ボタン、曲ごとの受渡トレイ、Drums／Bass／Keys別のMIDIカードを持たせる方針。
- DAW固有のコードトラック、Session Player設定、音源、プラグイン、ミックス設定は直接相互変換しない。受け渡す正本はMIDIノート・ベロシティ等の演奏データ。
- コード名の再解析、テンション／分数コード、ドラムノート配列は往復後に確認が必要。テンポと曲構成はCubase側を基準に維持する。

## つまずきから引く

- **Cubaseが全体的に重い（マシン性能は十分なのに）** → まず `スタジオ設定 → オーディオシステム → 詳細設定` の**「マルチプロセッシングを有効化」**を見る。オフだとCPUを1コアしか使わないため、どんな高性能機でも重くなる。ASIO-Guardもセットでオンにする（上の「現在の確定設定」参照）。プラグインやメモリを疑う前にここ。
- Bluetoothスキャンが終わらない → 別のMac/iPhone/iPadへの接続を切る。
- USBでは動くがBluetoothでMIDI Remoteが動かない → USBとBluetoothは別ポート。Bluetooth用サーフェスを使う。
- XYパッドが音程を鳴らす → Touch ScaleではなくX-Yモード。
- XYの動きがおかしい → X＝CC16、Y＝CC17、各0〜127を確認。
- CC番号が不明 → KORG KONTROL Editorで左の `X-Y` を選び、詳細欄を下へスクロール。中央図だけで判断しない。
- `.drm` など専用形式の自作ファイルが読み込み時に壊れた → 壊れた生成物への継ぎ足し修正を繰り返さない。まず正常動作する正本をコピーし、変更点を最小限に限定して最初から作り直せないか検討する。

## AIの作業原則（今回の失敗から）

- うまくいかなかった方式を、その前提のまま何度も修正し続ける傾向に注意する。
- 1回目の修正でも同じ症状が残った場合は、追加修正より先に「正常な正本から再作成」「別経路」「変更範囲の縮小」を検討する。
- 専用ファイル形式では、見た目のXML検証や行数だけで成功と断定しない。実際のアプリで読み込めることを成功条件にする。
- 今回のBFDドラムマップでは、正常版にあった `Order`、`OutputDevices`、`Flags` を落とした自作版がCubaseで全行Kickとして展開された。その不良版を修正し続けたのが失敗。
- 解決策は、正常版 `BFD3.drm` を正本としてMap部分を完全保持し、マップ名とOrderだけを変更して新規作成することだった。

## 4. 固定ワークフロー

### A. 毎日の早天

1. `早天編集スタジオ` を開く。
2. `毎日の早天` イベント内の `早天編集雛形` を `⌘D` で複製する。
3. 複製したプロジェクトを日付が分かる名前に変える。
4. 当日の動画を必要な本数だけ、基本は「ファイルをそのままにする」で読み込む。
5. 今日使う動画を選び、`option+X` で範囲指定を解除してから `E` でタイムラインへ入れる。複数本なら再生順に繰り返す。
6. 1本なら不要部分をカットする。複数本なら接続部も確認する。`Shift+Z` で全体表示し、冒頭、末尾、音量を確認する。
7. 必要な回だけSilenciで無音処理し、FCPで仕上げる。
8. H.264/AACで動画ファイルを書き出す。
9. QuickTimeで最初から最後まで確認してからアップロードへ進む。

### B. 賛美動画

1. 完成音源を読み込む。
2. 静止画または少数の映像カットを曲尺に合わせる。
3. 曲名など最小限のタイトルを置く。
4. 歌詞を載せる場合も、まず一部分で見た目と読みやすさを確定してから全体へ広げる。
5. 縦書きは、急ぐ場合はFCPで一文字ずつ改行する。再利用する場合はMotionの `Text > Layout > Direction: Vertical` で縦書きタイトルを作る。
6. H.264/AACで書き出し、QuickTimeで音量、文字切れ、冒頭・末尾を確認する。
7. 最初はYouTubeで限定公開し、Macとスマートフォンの両方で確認してから公開する。

### C. Silenci → FCP

1. Silenciで動画を開く。
2. `Language=Japanese`、モデルは速度優先なら0.6B、精度優先なら1.7B。
3. Analyze後、`Export → FCPXML`。
4. FCPで「ファイル → 読み込む → XML」。
5. 新規プロジェクトが自動生成される。既存プロジェクトは上書きされない。
6. 不要な字幕はインデックスの「タイトル／キャプション」からまとめて削除する。
7. 無音カットと接続部を再生してから、FCPで最終調整する。

## 5. 書き出しと公開前確認

- 1080pの目安: 24/25/30fpsは8Mbps、48/50/60fpsは12Mbps。

- 書き出したファイルの長さが想定どおり。

## 今日の早天編集を始める最短手順（2026-07-24実機確認）
- **ライブラリ**＝大きな仕事場、**イベント**＝素材とプロジェクトを入れる箱、**プロジェクト**＝実際に編集する一本の動画。
- 早天専用ライブラリ `早天編集スタジオ` を新規作成。古いライブラリは削除せずFCP上で閉じ、画面を整理した。
- ライブラリ作成時に日付イベントが1個だけ自動生成される。翌日以降にイベントが自動で増えるわけではない。イベントは `毎日の早天` として使い回す。
- プロジェクト `早天編集雛形` を作成。毎回作り直さず、プロジェクト本体を選んで `⌘D` で複製し、日付名へ変更して当日の動画を入れる。複製されるのは編集内容で、元動画ファイルそのものではない。
- 開始手順は、`早天編集スタジオ` → `毎日の早天` → `プロジェクト（1）` を展開 → `早天編集雛形` を選択 → `⌘D` → 複製側を日付名へ変更 → `⌘I` で当日の素材を読み込む。
- 素材は1本の日も複数本の日もある。1本なら不要部分をカットし、複数本なら再生順に並べて接続部を確認する。必ず2本を一本にする工程ではない。
- 素材はFinderからイベントへドラッグしてもよい。読み込み画面を使う場合、一過性の素材は「ファイルをそのままにする」。ビジュアル検索、最適化、プロキシ、音声解析、英語文字起こし、iXML割当はオフでよい。
- 2本を並べるときは、先に流す動画を選んで `E`、次の動画を選んで再度 `E`。`Shift+Z`で全体表示にし、接続部を再生確認する。
- 確認用の倍速再生は `L`を2回（`K`で停止）。完成動画自体の速度は変わらない。
- `R8/07/22（1）` などは、イベント内の素材を作成日別にまとめた「日付グループ」であり、プロジェクトではない。素材はプロジェクトで未使用でも表示される。
- **今回の実機結果**: 2026-07-24に、既存プロジェクトの複製→日付名変更→動画1本の読み込み→不要部分のカット→編集完了まで確認。
- 次回の呼び出し: `fcp97` の後に「今日も編集」と言えば、この開始手順から案内する。
- 最終確認: 2026-07-24

## 早天素材の実体と雛形の設定（2026-09-14実機確認）
- 撮影素材は `~/ムービー（Movies）` に `2026-09-14 06-50-16.mov` のような日付時刻名で置かれる。実体は **1920×1080 / 60fps / H.264 / 音声AAC 48kHz**（ffprobeで確認）。
- ライブラリ `早天編集スタジオ.fcpbundle` の保存場所は **`~/ムービー`**。旧ライブラリ `早天.fcpbundle` も同じ場所にあり、そちらには日付名イベントで素材をコピー取り込みしている。新規の日次編集は `早天編集スタジオ` 側で行う。

## メディアをタイムラインに載せる
- ブラウザでクリップを1回クリックして選ぶ
- `option + X` … 範囲選択（イン点・アウト点）を解除（頭から丸ごと入れるため）
- `E` … タイムライン末尾にアペンド（追加）
- `W` … 再生ヘッドの位置にインサート（途中に差し込む）
- タイムラインが無くて置けない → クリップを選んで `⌘N`（新規プロジェクト）

## 途中から始まってしまう
- 原因＝元クリップにイン点・アウト点が残っている
- 直し方＝クリップを選んで `option + X` で範囲をリセット

## 映像が映らない・重い
- 原因の筆頭＝ビューア右上「表示」が **プロキシ** になっている（プロキシ未作成だと真っ黒）
- 直し方＝「表示」を **最適化されたメディア／オリジナル** に戻す
- プロキシは基本 **作らなくてよい**。高性能マシンはオリジナルのままヌルヌル動く。重い素材で再生がカクつくときだけ使う

## タイムラインに映像の帯（サムネイル）が出ない
- タイムライン右上の表示切り替え（スイッチ型アイコン）が波形だけになっている
- フィルムストリップを含む表示に変えると絵が戻る

## ズームすると時間目盛り（ルーラー）が消える
- 消えたのではなく、拡大でクリップのない空白部分にスクロールしているだけ
- `Shift + Z` … タイムライン全体をウィンドウ幅に合わせて戻す
- その後、見たい所に再生ヘッドを置いてから `⌘ +`（拡大）/ `⌘ -`（縮小）
- ズームは常に再生ヘッド中心に効く → 先にヘッドを置くのがコツ

## 無音の自動カット（Silenci）※2026-07-18導入
- 2026-09-15: このMacにはSilenciAppが無かった。代替のAVAssetReader→RMS解析→FCPXML読込を実機検証。条件・限界・保存先は [[🎬 動画編集引き継ぎ（AI共通）]]「2026-09-15 無音カット実機検証」を参照。
- FCP自体に無音の自動検出は無い。外部の無料アプリ **Silenci**（GitHub: leeyc09/Silence-Cutter、Qwen3-ASR＋MLX、100%ローカル）を使う。導入済み。
- 流れ：Silenciで動画を **Open** → 解析設定で **Language=Japanese**／ASRモデル（0.6B=速い／1.7B=高精度）→ **Analyze**（初回はAIモデルDLで数GB）→ **Export → FCPXML**（デスクトップ等へ保存）→ FCPで **ファイル→読み込む→XML…** で取り込む。
- 取り込むと**新規プロジェクトが自動生成**される（自分で新規プロジェクトを作る必要なし。既存は上書きされない）。
- テロップ／字幕はFCPXMLに必ず埋め込まれる。**不要なら取り込み後にインデックスで「タイトル／キャプション」を選んでまとめてDelete**。テロップはFCP上で文言・見た目・タイミングも編集できる。
- 精度：**日本語の文字起こし精度はそれほど高くない**（2026-07-18実測）。「土台はSilenci、最終調整はFCP」の分担が現実的。
- 起動の一手間：署名なしアプリなので初回はブロックされる。**システム設定→プライバシーとセキュリティ→「このまま開く」＋認証**で起動。初回セットアップで **Homebrew** が要る（管理者パスワードでターミナルから手動インストール：`/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"` → 完了後アプリで Retry）。壊れている扱いのときは `xattr -cr /Applications/SilenciApp.app`。

## YouTube用に書き出す
- FCPの「共有」から「ソーシャルプラットフォーム」または「ファイルを書き出す」。
- 通常は **H.264映像＋AAC音声、音声48kHz**。
- 1080pの目安は、24/25/30fps＝8Mbps、48/50/60fps＝12Mbps。
- 書き出したファイルをQuickTimeで再生し、音量、文字切れ、冒頭、末尾、想定外の空白を確認してからYouTubeへ上げる。

## 縦書きタイトル

- 急ぐ場合は、一文字ずつ改行して縦書き風にする。

# AI関連モード

## 起動

1. 戦略・アプリ・説教・早天・音楽制作の台帳を最初から読まない。
2. `🤖 AI関連引き継ぎ（AI共通）.md` だけを最初に読み、相談内容に対応する正本へ進む。
3. 各正本は全文でなく、索引・見出しから関係する節だけ読む。
4. `ai97`だけが入力された場合は「AI関連モードを起動しました」と伝えて相談内容を待つ。

## 読み分け

- AIの役割分担、どのAIに何を任せるか: `🗂 話題別インデックス（AI共通）.md` の該当節
- LM Studio、ローカルモデル、外部API、OpenClaw、Copilot、Vault QA、RAG、画像・音声AI: `🤖 Obsidian×ローカルAI引き継ぎ（AI共通）.md` の該当節
- AI間の記憶、起動プロンプト、引き継ぎ: `🔌 外部AI連携（起動プロンプトと記憶プロトコル）.md` の該当節
- 特定アプリの実装: AIの役割を決めた後、`app97`または対象アプリの単体引き継ぎへ渡す
- 聖書・説教・早天、文書・制作物: AI選定だけ扱い、本文作業は各専用モードへ渡す
- 最新モデル、価格、仕様: 公式情報で最新確認し、確認日を残す
- 「前に」「続き」「どうするんだっけ」: 上記正本を固有名詞で検索し、不足時だけ相談ログの関連箇所を検索する。ログ全体は読まない。

## 進め方

- 目的を先に確認し、特定モデルやローカル／クラウドを守ること自体を目的化しない。
- 設定・導入・復旧へ入る前に、症状を直すより問題自体を消せる上位経路を先に確認する。最低限、①同じAI／アプリを対象端末へ直接入れる、②画面共有・コネクタ・API・既存ログインでAIが直接扱う、③公式ネイティブアプリ／自動セットアップ／移行機能を使う、④端末や役割分担を替える、を比較する。別端末へのコマンド転記やユーザー中継を一度でも求める前にこの確認を済ませ、二度目の転記依頼は禁止する。製品の導入・復旧は、記録済みの旧手順より現在の公式導入経路を先に確認する。
- 確認済みの現行構成、検討中の代替案、未検証の候補を分ける。
- モデルの能力と、現在のアプリ・APIから実際に使える機能を分ける。
- 費用、品質、画像・音声対応、プライバシー、Mac負荷、実装手間で役割分担する。
- 記録済み手順を実画面・設定値・実行結果で再確認する。
- 現実の設定・認証・画面操作は、難易度や「雑務」という印象で扱わず、`現在の状態を観測 → 一操作 → 実際の反応を確認 → 状態を更新` の制御ループとして扱う。期待した反応を確認するまで次の操作へ進まない。
- 期待した状態へ移らなかった場合は、説明や同じ操作の反復を始めず、最後に確認できた成功状態と最初の失敗状態を特定する。その区間だけを修復するか、その区間を通らない別経路へ切り替える。
- 視界拡張を物理的な画面・ログ・ミラーリングだけに狭めない。行き詰まり時は、現在の問題設定を仮説へ戻し、別の抽象度・別分野の類推・別の因果モデルから同じ事実を捉え直す。「不足している情報」だけでなく「自分がすでに知っているのに、現在の枠組みのため使っていない知識・機能・解法は何か」を明示的に検索する。
- ユーザーが提示した直近の具体例に新しく固定されない。その例が有効なら上位原理を抽出し、まだ提示されていない可能性まで探索する。複数端末・アプリの観測統合、ミラーリング、連携機能、ログ、通知、既存ツールは候補の一部であり、視界拡張そのものではない。
- 賛同や原則の説明を完了扱いにしない。ユーザーが「やって」と求めている場合は、その原則を直後の操作と検証に適用し、現実の成功状態まで確認する。
- 同じ経路が二度外れたら、正本復旧・別経路・変更範囲縮小を比較する。

## 終了時

- 変更内容に応じて、AI実行環境引き継ぎ／DS運用引き継ぎ／外部AI連携の該当正本だけを更新する（AI司令塔は2026-07-31に廃止。行き先は 🗂 話題別インデックス）。
- 再利用できる手順には「最終確認: YYYY-MM-DD」を残す。失敗した手順は修正するか「要精査」とする。
- 大きな方針変更だけ `🗒 相談ログ（追記式）.md` に短く記録する。
