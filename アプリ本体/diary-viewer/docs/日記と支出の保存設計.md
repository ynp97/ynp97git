# 日記と支出の保存設計

> 2026-09-08更新: 受け箱の保存・日付訂正・再起動・バックアップを実機検証し、日付確定の受け箱原文を日記一覧・検索・年別表示へ接続した。年別Markdownへの転記は未実装で、以下の正本分担は変えていない。現在地・検査・未完了は [[アプリ本体/diary-viewer/docs/2026-09-08_受け箱と日記表示の検証]] を参照。以下は設計であり、全機能を実装済みという意味ではない。

## 1. 目的と今回の範囲

Wordに書いた雑感、写真、動画、レシートを一つの入口へ放り込み、日付で振り返る。同じレシートから商品単位の支出も集計する。入力時の細かな分類は必須にしない。

2026-09-07の本人の要望に基づく、既存DiaryViewerの拡張設計。今回は仕様・保存構造・実装順・受け入れ条件を定める。アプリのコード、本人の日記・写真・支出データは変更していない。以下のデータ構造はCodexによる実装上の選択であり、実装・復元試験済みという意味ではない。

### 本人の要望として受け取ったこと

- レシートを雑に撮って投入し、後で食費などをできるだけ細かく集計したい。
- 読み間違いを直せる。レシートをもらわなかった支出も追記できる。
- レシートを見て、その日に何をしたか思い出したい。
- 映画などの自由なタグを残す。
- Word等の雑感は書いた日へつなげる。
- 動画も記録に含める。元動画を残し、日記から再生する方針に了承あり。
- 自分用として育てつつ、最終的な販売も目指したい。販売価格・方式・時期はこの会話では決めていない。

### 採用する構成と、提案に留まるもの

- 一つのアプリに「日記」「支出」「受け箱」を設ける。日記と支出は、同じ原本を参照する別のデータとして扱う。
- 月別・分類別集計と手修正を先に成立させ、AI読取はその入力経路として後から接続する。
- お出かけ単位のまとめ、割り勘・立て替え、修正からの分類学習、動画の時刻メモ・文字起こしは前の会話での**Codexの提案**。必須仕様として一括実装しない。後から足せる関連IDと来歴を用意する。
- 収入・口座残高・予算残額まで管理する要望はまだ受けていない。支出額から残高を推測しない。

## 3. 画面での使い方

### 受け箱

ファイルをドロップ／選択、文章を貼り付け、または直接入力する。まず原本を保存し、日付や読取結果が決まらなくても投入を完了できる。表示を「保存済み・日付確認待ち」「読取待ち」「金額確認待ち」「整理済み」に分ける。保存とAI処理の完了を混同させない。

レシートがない場合は「支出を追加」から日付・金額・内容を入力する。分類・タグ・日記本文は任意。レシートを後から付けても既存支出への添付となり、別支出を自動追加しない。

### 日記

一日の中に、複数の雑感、写真、動画、レシート、手入力支出を並べる。日付が同じだけで本文同士を一つに結合しない。レシートだけの日も表示でき、架空の日記本文をAIが生成する必要はない。

日付による同日表示と、本人が選んだ明示的な関連付けを分ける。ある文章の内容と買い物の目的が同じだとは自動判断しない。明示的な関連は後で日付を直しても保持し、画面には各記録の本来の日付を出す。

### 支出

期間・分類・店・タグで絞り込み、合計から取引、明細、原本写真、その日の日記へ進める。訂正画面は写真と明細を並べる。品名・数量・単価・行金額・日付・店名・分類を変更でき、変更の取り消しと履歴表示を用意する。

## 4. データの正本を一つずつ決める

| 対象 | 正本 | 再生成の可否 |
|---|---|---|
| 日記の文章 | `ジャーナル/YYYY.md` | DBの索引から勝手に再生成しない |
| Word・写真・動画・レシートの原本 | 管理フォルダ内の原本ファイル | 消したら戻せない。必ずバックアップ対象 |
| 支出・明細・分類・関連付け・手修正 | SQLite DB | キャッシュではない。必ずバックアップ対象 |
| AI抽出結果と読取履歴 | DB内の候補記録 | 採用値と区別して保持 |
| 日記検索索引・サムネイル | 再生成可能なキャッシュ | 元データから再生成可能 |
| 月別Markdown・CSV一覧 | DBからの書き出し | 正本から再生成可能 |

概念上の保存場所（本人が選ぶライブラリを起点とし、ユーザー名・絶対パスを埋め込まない）:

```text
選んだライブラリ/
  ジャーナル/YYYY.md
  media/ジャーナル写真/             既存写真＋新規写真・レシート
  media/ジャーナル動画/             元動画
  media/ジャーナル原本/             Word・PDF・貼付原文等
  日記アプリデータ/library.sqlite   明細・関連情報の正本
  日記アプリデータ/operations/      保存中断からの回復記録
  日記アプリデータ/staging/         保存確定前の一時コピー
  日記アプリデータ/exports/         Markdown・CSV・JSON＋対応表
```

原本はコピーし、サイズとSHA-256を検証してから参照を確定する。元の取り込み元ファイルは移動・削除しない。添付にはライブラリ相対パス、元名、種別、サイズ、ハッシュを保存する。外部の場所を参照する方式は初期版で混ぜない。

SQLiteを採る理由は、明細とその訂正・分類・関連の更新をDB内で一括確定できるため。**SQLiteのトランザクションだけでMarkdownや動画のコピーまで原子的になるわけではない**。複数ファイルの保存は§8の回復手順を必要とする。

Obsidian内では本文・添付を読める。家計一覧は「出力」と明記し、そこを外部編集してもDBへ黙って逆反映しない。家計の訂正はアプリから行う。外部編集を戻す機能を後で作る場合は差分を提示する取り込み処理にする。

## 5. 最小のデータモデル

すべての主キーは作成時に一度だけ発行し、再起動・編集・日付変更で変えない。

| 実体 | 必須の役割・主な項目 |
|---|---|
| Library | UUID、schemaVersion、設定。固有の利用者名や端末名に依存させない |
| Import | 投入ID、状態、投入日時、原本ID、処理の再開位置、エラー。再試行しても二重作成しない |
| JournalRecord | 永続ID、年月日、時刻（不明可）、タイムゾーン、ファイル内範囲、原文ハッシュ。文章そのものはMarkdownが正本 |
| Asset | UUID、相対パス、元名、サイズ、SHA-256、撮影日時候補、種別。原本と派生ファイルの関係 |
| Transaction | UUID、購入日、店、通貨、支出合計、支払方法（任意）、入力元、状態、改訂番号、返品元ID（任意） |
| LineItem | UUID、取引ID、印字品名、修正品名、数量・単位・単価（任意）、行金額。読み取れない欄はnull |
| Adjustment | 値引き・外税・端数調整等の金額と対象。内税の情報表示は二重加算しない |
| Allocation | 取引を分類へ配分する金額。品目・調整との対応と配分根拠を持つ |
| Extraction | 原本ID、実行ID、モデル／処理版、実行時点の改訂番号、抽出候補、根拠位置、検証結果。採用値を直接上書きしない |
| Revision | 対象ID、旧値・新値、変更日時、本人／抽出／ルール等の由来。取り消しも新しい改訂として保存 |
| Link / TagAssignment | 日記・添付・支出間の関連、タグ、話題の範囲、手動／提案の区別。日付だけを外部キーにしない |

レシートは取引そのものではなく証拠となる添付。1取引にレシート写真が複数枚あってよく、写真なしの取引も許す。同じ添付を複数の記録から参照しても、取引はUUID単位で一度だけ集計する。

同一ファイルの再投入はハッシュから既存原本を再利用する。別角度の写真は同じハッシュにならないので、店・日時・合計などから「重複候補」として確認できるようにする。同額の買い物を勝手に統合・削除しない。分割撮影は一つの読取単位として結合し、重なる品目の二重抽出を確認する。

### 既存日記のID

現在の `Entry.id = UUID()` は画面上の一時IDで、保存済み関連のキーには使えない。

- 初回は原本を変更せず、DBに既存エントリの原文範囲・ハッシュ・日時・出現位置と新規UUIDの対応を記録する。既存Day One UUIDがあれば由来として保存する。
- 同日時に複数件あるので日時だけで同一視しない。Day One UUIDの一意性も入力側で検証する。
- 再読み込み時に完全一致する元ブロックから再関連付けする。外部編集で候補が曖昧になったら別の日記へ付け替えず「関連先の確認待ち」とする。
- 新規エントリと本人が編集して保存するエントリには、原文を保つ保存処理で `<!-- diary-entry-id: UUID -->` を付ける。既存全件へのID挿入は初期導入時に勝手に行わない。
- 編集・年移動では同じIDを引き継ぐ。ゴミ箱移動でも保持する。日記の削除で関連支出・共有原本を連鎖削除しない。

## 6. 日付・Word・動画・タグ

### 日付

`取り込んだ日時`、`書いた日`、`購入日`、`撮影日時`を別の欄として保持する。日付だけしか分からない記録に偽の時刻を作らない。時刻がない日は同日の後ろなど安定した表示順を使い、取込時刻を「執筆時刻」と表示しない。

日付の採用順は、本人指定→明確な日付見出し／原本上の購入日／撮影メタデータ。ファイル作成・更新日時は補助候補に留める。複数の候補が食い違う場合や年がない場合は受け箱で確認できるようにする。タイムゾーン変更で日付だけの記録を前日にずらさない。

### Wordの投入

初期対象は `.docx` とテキスト／リッチテキストの貼り付け。旧 `.doc` 等は原本として受け取り、本文展開は対応外なら明示する。全形式に対応したと偽らない。

文書ファイルの原本と、抽出した原文のスナップショットを保存する。本文の言い換え・要約・誤字訂正はしない。表・脚注・画像などを完全にMarkdownへ再現できない場合は原本へ戻れるようにし、変換の制約を表示する。

日付見出しが明確な複数日文書は分割候補を作り、元文書・段落範囲との対応を残す。本文中に昔の日付が登場しただけでは分割しない。切れ目が曖昧でも文書全体は受け箱へ保存できる。ファイルが渡されない貼り付けでは「元Wordを保存した」とせず、受け取った貼付内容を原本扱いにする。

### 動画

原本コピー・撮影日候補・一言メモ・タグ・サムネイル・明示操作による再生を用意する。自動再生しない。拡張子だけで再生可とは判定せず、実際のデコード可否を確認する。再生できなくても原本を失わず「この形式はアプリ内再生に未対応」として外部で開けるようにする。

旧設計の200MB超での確認は当面維持。コピー前に必要な空き容量を確認し、進捗とキャンセルを用意する。サムネイル失敗と原本保存失敗を分ける。自動圧縮・自動文字起こし・外部AI送信は初期の投入処理へ含めない。

### タグと分類

本人が書いた `#映画` 等の本文タグは保持する。話題の行・段落へ紐付くタグを扱い、一日の全内容を一つの話題と決めつけない。AI提案は原文と別に保存し、本文への自動追記は行わない。原文変更で範囲がずれた提案は再確認する。

支出分類（例: 食費・日用品・娯楽）と自由タグ（例: 映画・作品名）は独立。分類名は後で変更可能、未分類も許す。タグを複数選んでも同じ取引を重複加算しない。気分タグを自動生成しない。`#EPOC` は本人だけが付ける。

## 7. 金額と訂正の規則

- 初期集計は日本円。金額は最小通貨単位の符号付き整数（円）で保存し、Doubleで金額を計算しない。数量・税率は必要なら十進数として扱う。未読を0円にしない。
- 通貨コードを保持し、異なる通貨を単純加算しない。外貨換算は初期対象外。
- レシートの合計、各品目、値引き、税の内外、端数を区別する。ポイント・クーポンの扱いが読み取れなければ候補状態のままにする。会計上の推測で合計を合わせない。
- 明細と調整の総和が採用合計と一致するか検証する。分類配分の合計も取引合計と一致させる。総額と明細の両方を合算して二重にしない。
- 合計だけ本人が確定した場合は、全額を「未分類」として集計できる。明細が確定してからその金額を配分する。
- 店全体の値引きは対象を確認できるまで未分類の調整に置く。按分する場合は整数円で端数を配り、配分方法と本人の採用を記録する。税額を推測して明細額へ二重加算しない。
- AI結果はまず候補。初期版では本人が取引単位で採用する。金額確認待ちを「確定支出」に混ぜず、件数と候補額を別表示する。分類だけ未確認なら未分類の確定支出として残せる。
- 日付・店名・明細・分類の手修正は履歴に残す。金額を変えたら合計と配分を再検証し、不整合のまま確定させない。
- 再読み取りは新しい候補を作るだけ。処理開始後に本人が修正した場合も、改訂番号を照合して手修正を保護する。採用前の候補との差分を見られる。
- 返品は原取引を消さず、返品日に負額の取引を作って原取引へ結ぶ。割り勘や立て替えを後で追加する際も、支払額と本人負担額を混同しない。

架空の検算例:

| 操作 | 期待値 |
|---|---|
| 食品800円＋日用品500円、値引き120円、合計1,180円 | 総支出1,180円。値引き配分前は800＋500−120（未分類調整） |
| 本人が値引きを食品74円・日用品46円へ配分 | 食費726円＋日用品454円＝1,180円 |
| レシートなしの映画代2,000円を追加 | 総支出3,180円、娯楽費2,000円 |
| 映画代に後からレシートを付ける | 総支出3,180円のまま |
| 日用品100円の返品を別取引として記録 | 対象期間の総支出3,080円 |
| 1,500円らしい読取候補を追加、まだ採用していない | 確定総支出3,080円、確認待ち1件 |

## 8. 保存・バックアップ・復元

日記の表示用パーサーを保存処理へ流用しない。ファイル全体の生バイト、対象エントリの正確な範囲、frontmatterとヘッダ、不明な行、コメント、改行形式を保持できる保存用ドキュメントモデルを用意する。

1. 原本を読み、想定するファイルハッシュと改訂番号を取得する。読取不能・形式不明・件数不一致・重複IDは停止理由とする。
2. 書込前に復旧用スナップショットを作る。初回は原日記一式、以後は変更ファイルとDBの整合した版を保存。旧方針のアプリ側退避＋Vault内バックアップを維持する。同じディスクの二つのコピーだけでは機器故障に耐えない点はバックアップ設定で区別する。
3. 添付をstagingへコピーして検証。変更後Markdownも一時ファイルへ書き、対象外のエントリ・原文がバイト単位で不変か、期待件数か検査する。
4. 同時書込を抑止し、書込直前に元ファイルのハッシュを再照合する。Obsidian等による外部変更があれば上書きせず競合として保持する。
5. 操作ID、旧新ハッシュ、退避先、段階を回復記録に保存してから確定する。原本の配置→Markdownの置換→DB内の関連・明細更新を進める。DB更新はトランザクションで行う。年またぎ・ゴミ箱移動も一つの操作記録に含める。
6. 全工程の照合後に「保存済み」を表示する。途中終了時は、次の起動で回復記録を読み、同じ操作IDで完了または旧版へ復旧する。どちらにも安全に決められない場合は原本・退避版を保持し、書込を停止する。

バックアップはDBだけでなく、日記・原本ファイル・関連の対応表・schemaVersionをまとめた整合スナップショットとする。キャッシュは省略可。開いたDBファイルだけを雑にコピーしない。ライブラリ移動・復元では件数とハッシュを照合する。

稼働中DBを複数端末からファイル同期して同時編集する方式は初期版の同期機能にしない。まず一台で整合性を確保し、端末間の移動は整合スナップショット経由。iPhoneの直接投入と複数端末同期は別工程で設計する。

データ書き出しは、日記Markdown、明細CSV、関連情報JSON、原本、ハッシュ一覧を含む。SQLite内の関係を失わず戻せる完全バックアップと、人が読める一覧書き出しを両方用意する。新しいschemaVersionを古いアプリで開いた場合は書き込まない。

## 10. 実装順と受け入れ条件

1. **保存の土台**: 永続ID・原文保持・競合検出・バックアップ・中断回復。架空ライブラリで検証し、既存閲覧との共存を確認する。
2. **一件を放り込める入口**: テキスト／Word一件・写真・動画を受け箱へ保存し、日付を確認して日記へ関連付ける。既存閲覧の年固定とパッケージ資源も直す。
3. **手入力できる支出台帳**: 写真あり／なし、明細訂正、分類、タグ、月次集計、返品、書き出し。AIがなくても家計機能が成立することを確認する。
4. **レシート読取の接続**: ローカルで架空または本人が指定したレシートを評価。小文字・内外税・値引き・複数枚を含め、候補→採用→訂正→再読取まで確認する。APIへの外部送信へ黙って切り替えない。
5. **日常運用と販売準備**: 実際に放り込み・振り返り・月集計を試し、iPhoneからの投入、導入、容量、復元を整える。配布形態・対応OS・依存物の再配布条件・価格等は販売工程で確認する。

次の実装は1。保存系はAstraの高を推奨する工程。工程の区切りで推論量を下げられるか伝える運用は今回のタスク内の合意として引き継ぐ。こちらから設定値を自動変更したとは言わない。

### 意味のある受け入れ確認

- 同日時の別エントリ、本文中の `##`、HTMLコメント、引用、絵文字、空本文、異なる改行を含む架空日記を使う。無編集の往復はバイト一致。1件追加しても既存部分が不変。
- 既存1,113件は以前の確認時点の件数。現在の実数は書込前に確認し、ハードコードで過去の件数へ合わせない。
- 日付移動・再起動・本文編集・ゴミ箱復元を経ても同じレシートと支出へたどれる。
- 日付不明のWord、文中の過去日付、複数日分、元Wordなしの貼付をそれぞれ扱い、原文が残る。
- §7の架空金額例を通す。タグ併用・添付追加・再読取でも支出件数と合計が増殖しない。
- 全保存段階で中断を模擬する。容量不足・コピー失敗・DB失敗・Obsidian側の競合でも原日記を失わず、再試行で二重化しない。
- 別の空ライブラリへバックアップから復元し、日記・明細・原本の件数、ハッシュ、関連を照合する。
- 各工程は `.app` を起動して画面と操作結果を確認して完了とする。ビルド・単体テストだけで「使える」と言わない。
